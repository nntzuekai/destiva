# Phase 2: live segment-level measurement

Phase 2 combines segment-level measurement with controlled dataset collection.
It measures how instruction characteristics affect the cost of validating
temporal segments. One observation is one exact pair of post-pass LLVM IR
states. Candidate pairs are generated by DESTIVA's temporal-decomposition
heuristics or an explicitly documented augmentation policy, then sampled so the
experiment does not enumerate all possible O(N²) pairs.

The current pipeline does **not** read the artifact's pre-generated
`*_passes.json` files. Pass order, instruction changes, characteristics, and
exact snapshots all come from the same live run of the instrumented LLVM build.
This removes the pass-sequence alignment problem found in the earlier pilot.

## What the pipeline records

`collect_live.py` invokes `opt` once per sampled function with the repository's
instruction-tracking LLVM instrumentation. During that one trace it:

1. observes the actual `default<O3>` leaf-pass sequence and distinguishes
   repeated pass names by occurrence number;
2. uses stable `!mymd` instruction identities to classify instructions as
   added, removed, or modified at each pass;
3. extracts opcode/category, operand, type, constant, memory, atomic, vector,
   call, CFG, and dependency characteristics;
4. applies the same temporal heuristics used by DESTIVA;
5. samples the candidate segments deterministically; and
6. writes only the post-pass snapshots needed by those sampled segments.

Each segment record contains four useful feature families:

- original-function controls (`input_features`);
- DESTIVA-style interval statistics such as modified-instruction total,
  concentration, entropy, span, and pipeline position (`features`);
- cumulative characteristics of changes made by all passes inside the interval
  and net characteristics obtained by directly comparing its endpoints
  (`features`); and
- complete start/end IR characteristics and their signed and absolute deltas
  (`boundary_features`).

The resulting schema-v3 manifest is authoritative. It embeds snapshot paths and
SHA-256 hashes, and its metadata records the live LLVM version, commit, pipeline,
sampling configuration, completeness, and digest. `run_segments.py`,
`qc_report.py`, and `merge_phase2.py` all reject an incomplete or modified
manifest.

Standalone `alive-tv --time-verify` emits one `PHASE2_TIME` record for the named
function. The runner records that internal verification time as the response
variable, as well as wall time, verdict, censoring, timeout, and environment
information.

## Earlier pilot files

Files produced by `make_manifest.py` and `extract_boundary_features.py` use the
old sidecar-alignment design. They remain in the repository only to document and
inspect the earlier pilot. Do not resume or merge them with this pipeline.
Schema-v3 results use
`measurement_method=live_snapshot_pair_v2`; choose new `pilot_v3_*` filenames.

## Setup

The patched LLVM build in this repository is required. An unmodified system
`opt` does not attach and propagate the `!mymd` identities used by the live
collector.

### Docker

Rebuild the image from the branch containing this implementation:

```sh
git switch mp
git pull
docker build -t destiva-phase2 .
mkdir -p mp/phase2/work
docker run --rm -it \
  -v "$PWD/mp/phase2/work:/root/destiva/mp/phase2/work" \
  destiva-phase2 bash
cd /root/destiva
```

The bind mount preserves profiles, snapshots, manifests, and results after the
container exits.

### Native Ubuntu 24.04

Use an Ubuntu 24.04 checkout of the same branch:

```sh
git switch mp
git pull
sudo apt-get update
sudo apt-get install -y \
  build-essential cmake ninja-build git python3 re2c zlib1g-dev util-linux
```

Build the patched LLVM, Z3, and Alive2 using the native setup in the repository's
main README. After applying the main instruction-tracking patch, apply the small
Phase 2 overlay that suppresses its redundant per-callback diagnostic output:

```sh
cd llvm-project
git apply ../mp/phase2/quiet-tracking-output.patch
cd ..
```

The live collector also cleans that output when used with an older build, so
the overlay affects collection speed rather than data semantics. If the tools
were already built before pulling this branch, apply the overlay and rebuild
LLVM and Alive2:

```sh
cmake --build llvm-project/build -j 16
cmake --build alive2-decomp/build -j 16
llvm-project/build/bin/opt --version
alive2-decomp/build/alive-tv --help 2>&1 | grep time-verify
mkdir -p mp/phase2/work
```

`util-linux` provides `prlimit`, used for per-process memory limits. The default
tool paths are `llvm-project/build/bin/opt` and
`alive2-decomp/build/alive-tv`; override them with `--opt` and `--alive-tv` if
needed.

## 1. Smoke-test live collection

This traces two functions and does not run Alive2 validation:

```sh
python3 mp/phase2/collect_live.py \
  --sample-functions 60 \
  --limit-functions 2 \
  --max-segments-per-function 12 \
  --profiles mp/phase2/work/smoke_v3_profiles.jsonl \
  --manifest mp/phase2/work/smoke_v3_manifest.jsonl \
  --snapshots-dir mp/phase2/work/smoke_v3_snapshots
```

Success requires `smoke_v3_manifest.metadata.json` to contain `complete: true`
and an empty `errors` array. This stage can produce substantial diagnostic IR,
but keeps it in memory and invokes `opt` only once per function.

## 2. Collect the 60 × 12 pilot

```sh
python3 mp/phase2/collect_live.py \
  --sample-functions 60 \
  --max-segments-per-function 12 \
  --profiles mp/phase2/work/pilot_v3_profiles.jsonl \
  --manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --snapshots-dir mp/phase2/work/pilot_v3_snapshots
```

The default pool contains end-to-end, mean, median, Top2, Fixed, Clustered4
(`dynamic_four`), and all-modified-pass clustering (`dynamic`). The sampler
always retains end-to-end and Clustered4 segments, then fills the remaining
budget round-robin across heuristics. A pair selected by several policies is
stored once with all policies in `selected_by`.

If collection is interrupted, rerun the same command with `--resume`. Completed
functions are skipped. If metadata reports a per-function error, fix its cause
and resume using the same paths. Use `--overwrite` only when intentionally
starting those outputs over.

Pass-by-pass is excluded by default because it can add roughly one segment per
pass. To include it, supply all requested policies explicitly:

```sh
python3 mp/phase2/collect_live.py \
  --sample-functions 60 \
  --max-segments-per-function 20 \
  --heuristics end_to_end all_passes mean median top2 fixed dynamic_four dynamic \
  --profiles mp/phase2/work/pilot_v3_pp_profiles.jsonl \
  --manifest mp/phase2/work/pilot_v3_pp_manifest.jsonl \
  --snapshots-dir mp/phase2/work/pilot_v3_pp_snapshots
```

`--max-segments-per-function 0` retains the complete union selected by the
requested policies. It still does not generate arbitrary pass pairs.

## 3. Preview validation commands

Execution is opt-in. This validates the manifest and every snapshot hash, then
prints commands without invoking Alive2 or Z3:

```sh
python3 mp/phase2/run_segments.py \
  --manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --output mp/phase2/work/pilot_v3_temporal_results.jsonl \
  --jobs 8
```

## 4. Measure temporal segments

Start with a small live batch:

```sh
python3 mp/phase2/run_segments.py \
  --manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --output mp/phase2/work/pilot_v3_temporal_results.jsonl \
  --timeout 600 \
  --memory-gb 4 \
  --jobs 8 \
  --limit 20 \
  --execute
```

After inspecting those records, remove `--limit 20` to finish the pilot. Output
is flushed after each run. Repeating the command resumes by skipping existing
`run_id` values. `--repeats 3` collects three measurements per segment when
runtime stability is needed.

To measure spatial plus temporal decomposition, use a separate result file:

```sh
python3 mp/phase2/run_segments.py \
  --manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --output mp/phase2/work/pilot_v3_combined_results.jsonl \
  --mode combined \
  --timeout 600 --memory-gb 4 --jobs 8 --execute
```

Separate files prevent temporal-only and combined costs from becoming one
ambiguous population.

## 5. Audit and create the analysis table

```sh
python3 mp/phase2/qc_report.py \
  --manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --results mp/phase2/work/pilot_v3_temporal_results.jsonl \
  --output mp/phase2/work/pilot_v3_qc.md

python3 mp/phase2/merge_phase2.py \
  --manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --results mp/phase2/work/pilot_v3_temporal_results.jsonl \
  --output mp/phase2/work/pilot_v3_dataset.csv
```

QC exits nonzero for incomplete coverage, duplicate IDs, snapshot or manifest
digest errors, invalid measurements, mixed schemas, or missing non-timeout
telemetry. The merge independently enforces the same gates and produces one CSV
row per run. Feature names beginning with `input_` are original-function
controls; `start_`, `end_`, `delta_`, and `abs_delta_` describe boundary states;
`cumulative_` describes all pass changes within the interval; and `net_`
describes the direct endpoint difference.

## Scaling after the pilot

The first expansion targets a deterministic 300-function sampling frame with
the same seed and 12-segment budget. The original 60 functions are the first
balanced subset of that frame. Exclude their live profiles so this batch runs
only the 240 new functions:

```sh
python3 mp/phase2/collect_live.py \
  --sample-functions 300 \
  --exclude-profiles mp/phase2/work/pilot_v3_profiles.jsonl \
  --max-segments-per-function 12 \
  --profiles mp/phase2/work/scale300_additional_v3_profiles.jsonl \
  --manifest mp/phase2/work/scale300_additional_v3_manifest.jsonl \
  --snapshots-dir mp/phase2/work/scale300_additional_v3_snapshots
```

This preserves the completed pilot rather than measuring those 60 functions a
second time. The expected additional batch is approximately 2,770 segments.
Based on the pilot, validation should take about 21 hours with eight jobs, but
server load and the realized timeout rate can change that estimate.

Preview, collect an initial batch, and then resume without `--limit`:

## Complete the DESTIVA heuristic union

The 12-segment cap measured 3,166 of the 4,221 unique segments selected by the
six DESTIVA cut-point heuristics across the 300 functions. Another 254 measured
segments are end-to-end-only baselines. Complete the six-heuristic union before
collecting non-heuristic augmentation segments.

The exclusion manifests are authoritative: the collector verifies their
digests, associated live profiles, and per-function pass-trace identities.
It then traces the same 300 functions and writes only heuristic pairs absent
from both earlier manifests. `--max-segments-per-function 0` disables the cap:

```sh
python3 mp/phase2/collect_live.py \
  --sample-functions 300 \
  --max-segments-per-function 0 \
  --heuristics mean median top2 fixed dynamic_four dynamic \
  --exclude-manifest mp/phase2/work/pilot_v3_manifest.jsonl \
  --exclude-manifest mp/phase2/work/scale300_additional_v3_manifest.jsonl \
  --profiles mp/phase2/work/heuristic_completion_v3_profiles.jsonl \
  --manifest mp/phase2/work/heuristic_completion_v3_manifest.jsonl \
  --snapshots-dir mp/phase2/work/heuristic_completion_v3_snapshots
```

With the current profiles this produces 1,055 segments from 247 functions. The
other 53 functions are deliberately retained as zero-segment profile records
because their heuristic unions were already complete. A different segment
count or a pass-sequence mismatch should be investigated before validation.

Preview, test 20 measurements, and then resume the same result file:
