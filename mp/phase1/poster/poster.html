Why temporal decomposition?

Translation validation proves that an optimized program preserves source semantics. SMT-based validation can time out when one query spans a large optimization gap.

DESTIVA inserts intermediate validation points, balancing one difficult end-to-end query against many pass-by-pass queries.

Current signal: the number of instructions modified by each pass. Equal-sized changes, however, can impose very different solver costs.

Research question

Can instruction, operand, memory, and dependency characteristics predict validation cost—and guide better cut-point selection?

Research program

1Function-level associationScreen feature families using saved validation outcomes.
2Segment-level measurementMeasure the cost of candidate temporal segments.
3Cost-aware decompositionPredict segment risk and optimize the cut set.
4Prospective evaluationTest generalization, performance, and correctness.

Design principles

  • Treat timeouts as censored observations—not successful 600-second runs.
  • Separate solver cost, solver-call overhead, and correctness risk.
  • Evaluate on held-out benchmark families to test generalization.
  • Count correct solves, not conditional speedup alone.

Phase 1 interpretation

What makes validation hard?Memory operations, pointer/address computation, and deeper dependency structure.
When does decomposition help?When modifications occur later, are farther apart, or interact with call/alloca/global-reference structure.

2

Segment-level measurement

Designed
Goal: replace whole-function proxies with observations tied directly to candidate temporal segments Pᵢ → Pⱼ.
  • Enumerate candidate boundaries: capture intermediate IR at pass boundaries and define segments with varied span, change magnitude, and pass identity.
  • Record boundary and delta features: instruction/opcode mix, operand types and widths, loads/stores/GEPs, calls and globals, dependency depth, pass position/gap, and spatial-slice size.
  • Measure outcomes: verdict, solver time, timeout, number of solver calls, extraction overhead, and fallback behavior under a fixed environment.
  • Control experiment size: stratify segment pairs by benchmark, span, and difficulty instead of running every O(N²) pair; retain all difficult and policy-selected cases.
  • Address runtime noise: repeat a representative subset and preserve timeouts as right-censored observations.
Output: a segment-level dataset connecting features available at cut-selection time to cost, timeout probability, and correctness.
3

Cost-aware temporal decomposition

Planned
Goal: turn segment-level predictions into a practical cut-point policy.
  • Predict cost and timeout risk: compare interpretable survival models with nonlinear models; calibrate predicted completion probability and runtime.
  • Prevent leakage: split by function and benchmark family so related segments cannot appear in both training and evaluation data.
  • Select boundaries globally: use dynamic programming or shortest-path optimization to minimize the sum of predicted segment costs plus per-call overhead.
  • Enforce safety: reject high-risk partitions, retain a trusted end-to-end or portfolio fallback, and model the Clustered4 incorrect cases separately.
  • Explain the policy: perform feature-family ablations and report whether memory, operand, dependency, and pass-location signals each add value.
partition cost = Σ predicted_cost(Pᵢ→Pⱼ) + λ·solver_calls + risk_penalty
Output: a frozen decomposition algorithm that chooses cut points from features observable before validation.
4

Prospective evaluation

Planned
Goal: determine whether the learned policy improves correct validation—not merely conditional runtime.
  • Baselines: end-to-end, pass-by-pass, Fixed, Top2, and Clustered4, plus an oracle analysis that estimates remaining headroom.
  • Generalization: evaluate on unseen functions and held-out benchmark families; report results both overall and per benchmark.
  • Paired analysis: compare the same transformations with confidence intervals and timeout-aware statistics.
  • Stress tests: vary timeout, solver-call penalty, hardware load, and feature availability; measure feature-extraction overhead.
